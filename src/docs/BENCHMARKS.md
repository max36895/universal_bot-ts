# Полные результаты тестов производительности `umbot`

> Все тесты проводились на чистой установке без сетевых вызовов, внешних API или пользовательской логики.  
> Измерялось **только время выполнения внутренней логики фреймворка**: от получения запроса до формирования объекта
> ответа.

---

## Сценарии производительности и замеры

Ниже приведены результаты тестирования времени выполнения **только внутренней логики фреймворка**,
исключая время выполнения `action`. Тесты проводились на системе с AMD Ryzen 5 5600G, 32 ГБ ОЗУ, SSD.

> **Примечание:** Время первичной загрузки новых изображений или аудиофайлов (когда `token` для файла ещё не
> кэширован в БД) **может значительно превышать 1 секунду** и выделено отдельно. После первой загрузки и кэширования,
> последующие обращения к тем же файлам выполняются быстро.

### Кэширование регулярных выражений

Особое внимание уделено оптимизации работы с регулярными выражениями (`RegExp`). При использовании `isPattern: true`,
`umbot` **кэширует скомпилированные `RegExp` объекты**.
Это означает, что при первом вызове `run()` с командами, использующими новые паттерны, происходит **компиляция `RegExp`**, что занимает больше времени.
При последующих вызовах с теми же паттернами, **скомпилированные `RegExp` берутся из кэша**, что **значительно ускоряет** выполнение.
Также в фреймворке предусмотрена группировка регулярных выражений из разных команд.
То есть когда задано множество команд с регулярными выражениями, эти регулярные выражения объединяются в группы, для
уменьшения количества обращений.

### Сравнение с реальными фреймворками

Стенд `benchmark/comparison/` сравнивает umbot с реальными фреймворками
конкурентов по платформам. У стенда собственный
`benchmark/comparison/package.json` (зависимости-конкуренты не попадают в
package.json репозитория). Каждый стенд — отдельный файл: сценарии, lockstep,
метрики и печать общие (`runner.js`), файл платформы задаёт вход и подключает
конкурентов. Запуск:

```bash
npm i --prefix benchmark/comparison
npm run compare        # Telegram: umbot vs grammy, telegraf
npm run compare:alisa  # Alisa: umbot vs yandex-dialogs-sdk
npm run compare:vk     # VK: umbot vs vk-io (+ @vk-io/hear)
npm run compare:viber  # Viber: umbot vs viber-bot
npm run compare:max    # MAX: umbot vs @maxhub/max-bot-api
```

Файлы стендов устроены одинаково (`telegram.js`, `alisa.js`, `vk.js`,
`viber.js`, `max.js`): `makeUpdate` — апдейт платформы, `umbot` — адаптер
и botType, `competitors()` — офлайн-путь каждого конкурента (обработка через
штатный `handleUpdate`/`handleRequest`/`handleWebhookUpdate`, без сети).
Добавление нового конкурента: пакет — в dependencies
`benchmark/comparison/package.json`, реализация — в `competitors()` файла
платформы по образцу существующих.

Дополнительно в `benchmark/comparison/`:

- **Стресс-стенд** `stress.js` (запуск: `npm run stress:compare:vk` и т.п.,
  или `node stress.js <файл> [сек] [окно]`) — поведение под непрерывным
  потоком: окно 200 запросов in-flight, 30 с, трафик-микс
  (точное/частичное/регулярка/fallback = 40/25/25/10), ротация 1000
  user_id, 1000 команд. Метрики: агрегатный RPS под потоком (не путать
  с `1000/p50` тепличного стенда — другой режим), p50/p95/p99, доля
  времени в GC, тренд пола кучи (пила мусора — норма, рост пола —
  проблема), retained-дельта после финального GC (утечка). Каждый
  участник — в изолированном дочернем процессе: падение одного по heap
  limit роняет только его строку.
- **Cold-start и IQR** — встроены в основной стенд: время первых 200
  запросов после регистрации без прогрева (прода-метрика serverless:
  латентность первого запроса после подъёма инстанса; печатается
  отдельным блоком — числа несопоставимы со steady-state) и
  межквартильный размах p75−p25 (ширина ядра распределения; p95
  дёргается от единичных выбросов ОС, IQR устойчивее).
- **Регрессионный baseline** `baseline.js` для CI night-job:
  `npm run baseline:update` — записать p50 umbot на маркерном сценарии
  «50 команд, точное совпадение» всех пяти стендов;
  `npm run baseline:check` — свериться (допуск +15% JIT-шума; exit 1 при
  регрессии). Ловит «кто-то занёс тяжёлый RegExp-компайл в горячий путь»
  автоматикой, а не ручным прогоном. Baseline-файл создаётся на той же
  машине, где гоняется check.

Честность стенда (едина для всех платформ):

- **Один вход для всех**: одинаковый апдейт платформы (структура байт в байт).
  umbot подключён штатным адаптером платформы; конкуренты обрабатывают его
  своим штатным офлайн-путём (`handleUpdate` у grammy/telegraf/max-bot-api,
  `handleRequest` у yandex-dialogs-sdk, `handleWebhookUpdate` у vk-io,
  `_handleEventReceived` у viber-bot).
  `botInfo` конкурентам задаётся явно (документированная опция/свойство),
  иначе их `handleUpdate` ходит за `getMe` в сеть.
- **Сеть исключена у всех**: команды umbot ставят `ctx.skipAutoReply = true`
  (без него его getContent ушёл бы в API платформы — мерился бы интернет);
  у конкурентов `ctx.reply`/`ctx.send` не вызывается. VkAdapter в стенде
  работает с `vk_load_user_info: false` — иначе адаптер по умолчанию ходит
  в VK API за именем пользователя на каждое сообщение.
- **Семантика выровнена**: подстрочный матч у всех — конкурентам команды заданы
  как `hears(new RegExp(...))`/аналог (единая обёртка `asRegExp` в `runner.js`;
  до выравнивания их `hears(строка)` матчит только точное совпадение —
  проверено по исходникам и поведенческим тестом на каждой библиотеке:
  grammy — `txt === t`, telegraf и max-bot-api — `new RegExp('^…$')`,
  @vk-io/hear — `text === condition`, viber-bot строковых триггеров не имеет).
  RegExp-вариант — их честная цена той же семантики, что у umbot-слота.
- Lockstep-чередование раундов (интерливинг: в каждом раунде все участники
  идут по очереди — тепловой дрейф CPU распределяется на всех поровну),
  медиана из 10 раундов; латентность каждого запроса замеряется отдельно
  (отсюда p95).
- **Пауза после регистрации команд (100 мс у vk-io/viber/max/alisa, 50 мс в
  каркасе) — у всех участников**: регистрация не мгновенна (umbot пересобирает
  снимок команд и компилирует RegExp, конкуренты recompose-ят/достраивают
  middleware-цепочки) — хвосты инициализации не должны попадать в замер.
- **Прогрев до плато (методика v4)**: до измеряемой серии каждый участник
  гоняется циклами по 500 запросов, пока медиана цикла перестаёт улучшаться
  (до 20 циклов = 10 000 запросов). Причина: кривая tier-up/inline-кэшей V8
  сходит на плато только через тысячи вызовов. С фиксированным прогревом
  2×500 запросов стенд ловил участников на крутом участке кривой: у
  «толстого» фреймворка (umbot: контроллер на 30 полей, ленивые компоненты,
  больше полиморфных call-site'ов) выход на плато медленнее, и он выглядел
  медленнее собственного steady-state. Замер кривых на VK, «6 команд,
  точное совпадение», медианы по 5 раундам: umbot 1.94 → 1.37 → 0.89 мкс
  (500/1000/2000 прогрева), vk-io 2.11 → 1.62 → 0.85 мкс — при прогреве
  ≥4000 запросов разрыв схлопывается в паритет 0.85 против 0.85 мкс.
  Старые таблицы «vk-io быстрее на 6 командах на 0.4 мкс» — артефакт
  недопрогрева, не свойство кода.
- **Латентности и память — раздельные фазы**: вся фаза
  латентностей идёт без единого вызова GC; фаза памяти (с forceGC)
  запускается только после её завершения. Пока фаза памяти стояла в том же
  раунде, каждый следующий раунд наследовал только что скомпактированную
  кучу: полный GC — это compaction, после которого V8 восстанавливает
  inline-кэши несколько запросов (полиморфный путь — дольше монолитного), и
  pooled p50 взлетал у обеих сторон в ~1.5 раза (матрица методик, VK,
  6 команд: с forceGC перед замером 3.0/2.2 мкс; фаза памяти в том же
  раунде 3.4/3.3; без GC вовсе 2.3/2.3 — паритет; steady-эталон 1.7/1.2).
  GC в замере измерял чувствительность к compaction, а не стоимость
  маршрутизации.
- **Победа — только при отрыве >5% и >0.3 мкс**: при меньшей разнице строки
  помечаются «паритет» (шум прогона), а не «лучший» у обоих.

Как читать (честно, включая неудобное):

- **umbot лучший во всех 13 сценариях Telegram** (методика v4: прогрев до
  плато, латентности без GC, раздельные фазы). Сюда входят и оба «6-командных»
  сценария, на которых раньше уступали grammy: 1.5 против 3.4 мкс (exact) и
  1.7 против 2.8 (regex). telegraf — ни в одном.
- **Группировка RegExp-слотов**: команды, у которых все слоты — готовые
  RegExp, теперь включаются в группы регулярок (как явные isPattern).
  «1000 команд, регулярка»: 39.9 мкс против ~50 до правки — combined-тест
  группы заменил линейный скан 500 регулярок до середины списка. Смешанные
  слоты (строка + RegExp) в группу не попадают: их приоритет относительно
  строковых команд задаётся позицией в списке, а группа матчит «первый
  подходящий».
- **С ростом числа команд разрыв растёт** (50 команд: umbot впереди 5.0–8.9×;
  500–1000 команд: 8.3–212×) — цена middleware-цепочки у конкурентов
  пропорциональна числу команд, у umbot точное совпадение O(1), скан —
  лёгкий индексированный цикл.
- **Мусор: umbot 4.6–4.8 КБ/запрос против 13.2–126.3 КБ у конкурентов** — в
  2.8–27.5 раз меньше нагрузки на GC при том же трафике (в regex-сценариях
  при 1000 командах у umbot 7.5 КБ — матч-массивы exec группы; всё равно
  до 15.8 раз меньше конкурентов; в стрессе VK и Viber память сравнима — паритет).
- Утечек нет ни у кого (retain ≈ 0) — честная ничья.
- Дополнительно (замер в изолированном процессе на каждого): при всплеске 2000
  одновременных запросов umbot отрабатывает за ~0.1 с при 16 МБ кучи; grammy —
  11+ секунд и 3 ГБ кучи; telegraf падает по heap limit Node (~4 ГБ): его
  debug-callback'и удерживают ctx-хвосты после завершения промисов.

При этом umbot единственный из трёх даёт 7 платформ, шаги, формы, NLU, state
и ReDoS-защиту из коробки — конкуренты сравнивались в их единственной
(Telegram) дисциплине.

Как читать (честно, включая неудобное):

- **Алиса (yandex-dialogs-sdk)**: umbot впереди во всех 13 сценариях —
  от 1.7 против 3.1 мкс (6 команд) до 35.7 против 207.7 (1000 регулярка)
  и 41.9 против 248.0 (1000 fallback). SDK не обновлялся с 2022, но это
  самый скачиваемый фреймворк Алисы в npm; у него нет аналога команд-шагов
  уровня фреймворка — его Stage/Scene-механика опциональна и в стенд не
  входит. Для Марусии и SmartApp сторонних фреймворков в npm нет —
  сравнивать не с кем.
- **Малые боты на VK (6–50 команд)** — единственная зона остаточных
  отставаний, и она узкая: vk-io быстрее только на «6 команд, точное»
  (1.1 против 1.6 мкс); «6 регулярка» (1.1 против 1.4), «50 точное/частичное»
  (2.4 против 2.4 и 3.4 против 3.4) и «1000 fallback» (49.8 против 51.3) —
  паритет. Это цена полного пайплайна (state, NLU, межплатформенная
  маршрутизация, метрики), которого у однострочных роутеров конкурентов
  нет. Важно: старые таблицы с разрывом 0.4 мкс на «6 точное» были
  завышены недопрогревом (участник мерялся на крутом участке JIT-кривой) —
  после перехода на прогрев до плато счёт VK изменился с 6+1 на 8+1 из 13;
  после выравнивания семантики (asRegExp) и починки порога победы в
  markRow (см. ниже) — 8 побед и 5 паритетов из 13.
- **Regex-сценарии при 500–1000 командах**: группировка RegExp-слотов даёт
  umbot «в 1.4–5.8×» против каждого конкурента (1000 regex: 36.2 против
  51.7 у vk-io, 36.6 против 143.5 у viber-bot, 36.2 против
  165.1 у max-bot-api, 35.7 против 207.7 у dialogs-sdk).
- **500–1000 команд (остальное)**: umbot впереди у всех по победам;
  fallback-сценарий VK (1000 fallback: 49.8 против 51.3 у vk-io) — паритет
  в пределах порога шума. vk-io — в 1.1–19×, viber-bot — в
  4.5–67×, max-bot-api — в 5.5–109×, dialogs-sdk — в 3.9–93×.
- **Малые базы MAX (6 команд)**: оба сценария — паритет (1.5 против 1.4
  мкс exact и 1.6 против 1.5 regex): отрыв 0.1 мкс ниже порога шума стенда
  (0.3 мкс). С 50 команд umbot впереди во всех сценариях MAX.
- **Viber (6 команд, регулярка)**: viber-bot быстрее (2.2 против 1.9 мкс —
  отрыв 0.3 мкс на границе порога, засчитан победой) — его
  matcher-роутер (линейный Array.find по exec) не создаёт контроллера и
  NLU; на остальных 12 сценариях umbot впереди.
- **Память на запрос**: umbot стабильно тратит 4.3–4.8 КБ (в regex-сценариях
  при 1000 команд — 7.2–7.5 КБ: матч-массивы exec группы); vk-io при 1000
  командах — до 100 КБ, max-bot-api — до 116 КБ, viber-bot — до 25 КБ,
  dialogs-sdk — до 89 КБ. Разница в 5.3–26 раз.
- **Оговорка про viber-bot и dialogs-sdk**: viber-bot — единственный
  полноценный фреймворк Viber в npm и не обновлялся с 2022; yandex-dialogs-sdk
  тоже не обновлялся с 2022. «Победа» против них не доказывает
  технологического превосходства, но показывает порядок величин.

#### Поведение под непрерывным потоком (стресс-стенд)

Стресс-стенд (`stress.js`, см. выше) меряет не латентность отдельного
запроса, а поведение под потоком: окно 200 запросов in-flight, 30 с,
микс 40/25/25/10 (точное/частичное/регулярка/fallback), 1000 команд,
ротация 1000 разных user_id. Результаты (Windows 10, Node 24):

| Стенд    | Участник    |  Запросов |    RPS     |   p50    |   p99    | GC, % времени | Утечка           |
| :------- | :---------- | --------: | :--------: | :------: | :------: | :-----------: | :--------------- |
| VK       | **umbot**   | 1 779 200 | **58 879** |  2.9 мс  |  5.6 мс  |      0.3      | 8.7 КБ/1000з*    |
|          | vk-io       |   820 758 |   27 128   |  3.7 мс  |  8.6 мс  |      4.8      | 8.3 КБ/1000з*    |
| Telegram | **umbot**   | 1 549 000 | **51 260** |  3.3 мс  |  7.2 мс  |      0.4      | 10.1 КБ/1000з*   |
|          | grammy      |     6 940 |    228     |  925 мс  | 1 305 мс |     65.2      | нет              |
|          | telegraf    |     4 608 |    151     | 1 312 мс | 2 345 мс |     66.4      | **177 КБ/1000з** |
| Alisa    | **umbot**   | 1 953 200 | **64 633** |  2.6 мс  |  6.3 мс  |      0.3      | 8.0 КБ/1000з*    |
|          | dialogs-sdk |    63 104 |   2 085    |  88 мс   |  143 мс  |     15.8      | 11.3 КБ/1000з*   |
| Viber    | **umbot**   | 1 885 015 | **62 380** |  2.7 мс  |  5.6 мс  |      0.3      | 8.3 КБ/1000з*    |
|          | viber-bot   |   160 695 |   5 314    |  18 мс   |  52 мс   |      0.4      | 8.2 КБ/1000з*    |
| MAX      | **umbot**   | 1 755 600 | **58 093** |  2.8 мс  |  6.8 мс  |      0.4      | 8.9 КБ/1000з*    |
|          | max-bot-api |    14 969 |    495     |  385 мс  |  526 мс  |     65.3      | **57 КБ/1000з**  |

\* «тёплый набор»: разовый retained-рост (JIT-кэши, кэш регулярок групп),
не линейный — см. разбор ниже.

Как читать (честно, включая неудобное):

- **Агрегатный RPS ≠ 1000/p50 тепличного стенда.** Под потоком латентность
  отдельного запроса растёт у всех (очередь задач), но umbot переваривает
  поток в 2.2 (VK) и в 11.7–339 раз (остальные платформы) больше запросов
  в секунду.
- **«Утечка» umbot 8–10 КБ/1000 запросов — не утечка, а тёплый набор**:
  диф-диагностика сериями (две одинаковые серии в одном процессе) показала
  спад retained на 1.2 МБ между сериями — рост одноразовый, линейного
  ретеншна нет. А вот telegraf (177 КБ/1000з) и max-bot-api (57 КБ/1000з)
  под потоком показывают настоящие retained-росты — тепличный стенд их
  не видел.
- **Почему разрыв в стрессе больше, чем в тепличном стенде: это не
  махинация, а два разных режима работы.**
    - Тепличный стенд (латентность одного запроса) честно показывает паритет
      каркасов: на «6 командах» vk-io даже быстрее (1.1 против 1.6 мкс),
      всё в пределах пары микросекунд. На малых ботах разницы почти нет.
    - Стресс вскрывает архитектуру: у конкурентов матчинг — линейная цепочка
      с аллокациями на каждом шаге, выполняемая на каждый запрос. При 1000
      команд и непрерывном потоке мусор генерируется быстрее, чем GC
      успевает его собирать: grammy/telegraf/max-bot-api проводят 65% времени
      теста в GC, очередь растёт, латентность уходит в секунды. umbot на
      точное совпадение имеет exact-хэшмапу (O(1), ноль скана), регулярки
      группируются в combined-RegExp (один прогон вместо 500), контроллер
      и компоненты создаются лениво — мусора на порядок меньше (0.3–0.4%
      времени в GC), пол кучи плоский (12→12 МБ).
    - Отдельный случай — **yandex-dialogs-sdk (Алиса, 64 633 против 2 085
      RPS)**: его роутинг устроен как `Promise.all` по ВСЕМ зарегистрированным
      командам (проверено по исходникам: `CommandsGroup.getMostRelevant`
      создаёт промис на каждую команду на каждый запрос и не может выйти
      рано — ему нужен максимум «релевантности» для Levenshtein-матчинга
      «похожих фраз»). 1000 команд = 1000 промисов и 1000 `toLowerCase`
      на каждый запрос. Это не баг стенда и не подтасовка — это цена его
      API. umbot такой семантики не предлагает (и не платит за неё):
      если нужен fuzzy-матчинг, его делают NLU-плагином отдельно.
    - **viber-bot — единственный конкурент в строю под потоком** (5 314 RPS,
      GC 0.4%): его внутренний matcher лёгкий. Но 12× разрыва по пропускной
      способности достаточно для вывода.
- **Важный эксцесс при подготовке стенда**: без fallback-команды `*`
  базовый контроллер umbot на промахе ставит `empty_text` без
  `skipAutoReply` — и адаптер честно шлёт ответ в API платформы. Для
  офлайн-стенда это означало реальные fetch-таймауты по 30–100 мс на
  каждом 10-м запросе. Стресс-стенд регистрирует `*` с `skipAutoReply`
  (как и compare-стенд в fallback-сценарии). Это же напоминает: в проде
  промах без ответа — это не «ничего не произошло», а сетевой вызов.

#### Cold-start (serverless-метрика)

Время первых 200 запросов после регистрации команд, без прогрева
(прода-метрика Cloud Functions: латентность первого запроса после подъёма
инстанса). Числа несопоставимы со steady-state — холодный JIT платит
первый запрос в десятки раз дороже плато. Сравнивать участников между
собой корректно: условия старта одинаковы. VK-стенд (Windows 10,
Node 24):

| Сценарий               | umbot: 1-й / ср. холодных, мкс | vk-io: 1-й / ср. холодных, мкс |
| :--------------------- | :----------------------------: | :----------------------------: |
| 6 команд, точное       |          4 530 / 51.5          |          1 171 / 14.3          |
| 50 команд, точное      |           173 / 11.7           |            35 / 5.0            |
| 500 команд, точное     |           255 / 17.5           |           148 / 37.3           |
| 1000 команд, точное    |           133 / 8.7            |           502 / 53.0           |
| 1000 команд, регулярка |         1 650 / 103.2          |         2 001 / 117.6          |

Как читать: на малых базах vk-io стартует легче (проще каркас — меньше
кодогенерации V8), но с 500+ команд umbot и в холодном старте впереди
(точное совпадение O(1) не требует прогрева), а на регулярках холодная
компиляция combined-RegExp у обоих сопоставима.

### Общая картина по всем платформам

Сводка по двум методикам: «тепличный» стенд (латентность одного запроса
после выхода на плато) и стресс-стенд (30 с непрерывного потока, окно
200 in-flight, 1000 команд, ротация 1000 пользователей).

| Конкурент          | Тепличный стенд (13 сценариев)               | Стресс (RPS под потоком)        | Память на запрос       |
| :----------------- | :------------------------------------------- | :------------------------------ | :--------------------- |
| grammy (Telegram)  | umbot лучше во всех 13                       | 51 260 против 228 (**225×**)    | в 1.8–26.3 раз меньше  |
| telegraf           | umbot лучше во всех 13                       | 51 260 против 151 (**339×**)    | в 3.4–28.6 раз меньше  |
| yandex-dialogs-sdk | umbot лучше во всех 13                       | 64 633 против 2 085 (**31×**)   | в 2.7–20.2 раз меньше  |
| vk-io              | umbot лучше в 8, паритет в 5                 | 58 879 против 27 128 (**2.2×**) | в 9–21.7 раз меньше    |
| viber-bot          | umbot лучше в 12; **уступает в 1** (6 regex) | 62 380 против 5 314 (**12×**)   | в 3.5–5.7 раз меньше   |
| max-bot-api        | umbot лучше в 11, паритет в 2 (6 команд)     | 58 093 против 495 (**117×**)    | в 13.5–22.2 раз меньше |

Где umbot честно уступает (и почему — это цена функциональности):

- **vk-io, «6 команд»**: 1.1 против 1.6 мкс (точное) — 0.5 мкс; «6 регулярка»,
  «50 точное/частичное» и «1000 fallback» — паритет. У vk-io нет пайплайна:
  он не создаёт контроллер с 30 полями, не ведёт state/NLU/метрики. Разрыв
  остаётся и после выхода на плато — это подтверждённая константа каркаса,
  а не артефакт замера.
- **viber-bot, «6 команд, регулярка»**: 2.2 против 1.9 мкс у viber-bot
  (отрыв 0.3 мкс — на границе порога) — его matcher-роутер не создаёт
  контроллера; на остальных 12 сценариях umbot впереди.
- **Cold-start на малых базах** (6–50 команд): 1 171 против 4 530 мкс
  первого запроса — vk-io проще, V8 компилирует его быстрее.

Где umbot стабильно лучше:

- **Память**: во всех сценариях тепличного стенда у всех конкурентов — в
  2.8–27.5 раз меньше транзиентного мусора на запрос (в стрессе VK/Viber —
  паритет); в стрессе у телеграм-конкурентов это выливается в 65% времени
  в GC против 0.3–0.4% у umbot.
- **Средние и большие базы (500–1000 команд)**: 1.3–2.6 мкс против
  24.6–403 у конкурентов на точном матче (exact-хэшмапа O(1) против
  линейной middleware-цепочки).
- **Стресс-режим** — главный разрыв. Именно под непрерывным потоком
  оптимизации umbot (O(1) exact-поиск, группировка регулярок в один
  combined-RegExp, ленивые контроллер/компоненты, снимок команд вместо
  итератора Map) превращаются из «паритета в микросекундах» в разрыв
  2.2–339× по пропускной способности: конкуренты тратят 65% времени на
  сборку собственного мусора, umbot — 0.3–0.4%.
- **Отсутствие утечек**: под потоком retained-рост umbot — разовый тёплый
  набор (~10 КБ/1000 запросов, спадает между сериями); у telegraf
  (177 КБ/1000з) и max-bot-api (57 КБ/1000з) — линейные росты.

Практический вывод: на малых ботах (до ~50 команд) при выборе между
umbot и vk-io решающим будет не быстродействие (разница 0.3–0.5 мкс
неощутима на фоне сетевого круга платформы в 50–300 мс), а функциональность
(мультиплатформенность, шаги, NLU, state). На нагруженных ботах (100+
команд, реальные RPS) запас прочности umbot по пропускной способности
и памяти — от 2× до двух с половиной порядков.

### Для каких сценариев создан umbot, а для каких — нет

Честная оценка границ инструмента (а не только его сильных сторон):

**umbot создан для:**

- навыков и ботов, управляемых **текстом**: команды, фразы, fallback-реакции,
  многошаговые диалоги (`addStep`), формы-опросники (`addForm`);
- **мультиплатформенности**: одна бизнес-логика на 7 платформ (Алиса, Маруся,
  SmartApp, Telegram, VK, MAX, Viber) — включая голосовые с TTS, кнопками,
  карточками и NLU;
- продуктов, где важна **предсказуемая ресурсность**: постоянное потребление
  памяти, отсутствие утечек (48-часовой стресс-тест), в 2.8–27.5 раз меньше мусора
  на запрос, чем у типичных Telegram-фреймворков;
- высоконагруженных навыков: health-check, метрики, rate-limiting middleware,
  ReDoS-защита из коробки.

**Сценарии, где потребуется дополнительная логика на вашей стороне:**

- **Не-текстовые апдейты**: декларативный роутинг по типу события есть —
  `bot.addEvent('photo' | 'voice' | 'callback' | 'inline' | ...)`, 17
  универсальных типов, адаптеры платформ объявляют поддержку через
  `supportedEvents` (валидация и предупреждения при подключении).
  Доп. код потребуется только там, где нужна глубокая платформенная
  специфика события (например, бизнес-логика по полям, которые нет смысла
  унифицировать) — читайте `controller.eventType`, `controller.payload`
  и `requestObject` прямо в хендлере события;
- **Telegram-only-специфика глубокого уровня**: обвязка «одной строкой»
  для частых сценариев есть — событийный роутинг `bot.addEvent(...)` +
  кросс-платформенный API-фасад `ctx.api?.sendPhoto/sendDocument/
sendAudio/sendVideo/answerCallback` (с матрицей поддержки по платформам
  и `can(method)`, см. api-reference.md). Однако полный охват Bot API
  (web-app, payments, games, бизнес-режимы и прочий длинный хвост методов)
  остаётся за `TelegramRequest` — вызовы собираются вручную через
  API-клиент;
- **Экстремальные базы команд** (>10 000 статических строковых команд):
  линейный скан при промахе честно задокументирован выше — для таких объёмов
  фреймворк сам рекомендует параметризованные команды/NLU/внешний API
  (см. `bench`-вывод), либо включите `re2` для регулярных выражений.

**Ключевая мысль:** umbot — не «универсальный фреймворк на все случаи», а
инструмент для сценария «диалоговый бот/навык на многих платформах с
предсказуемыми ресурсами». Если ваш продукт — диалоги, команды и шаги, вы
получаете всё из коробки и производительность выше конкурентов. Если ваш
продукт — обработка медиа-потоков или тонкая Telegram-специфика, взвесьте:
дополнительный код на umbot против отказа от 6 других платформ и
ресурсной эффективности.

### Проверка доступной памяти в бенчмарках

Бенчмарки `bench` и `stress` перед запуском проверяют, хватит ли памяти.
Проверка учитывает три реальных ограничения: лимит heap V8 (`--max-old-space-size` или ~4 ГБ
по умолчанию — даже при 16 ГБ RAM Node не аллоцирует больше), cgroup-лимит (docker/k8s) и
физическую память с учётом page cache (ядро сбрасывает кэш при нехватке — `os.freemem()`
на unix занижает доступное, из-за чего тест ложно отказывался в запуске). Оценка потребления
основана на фактических замерах: ~466 Б на строковую команду, ~0.8 КБ на isPattern-команду,
~1.6 КБ с учётом фрагментации V8 кучи при экстремальных количествах.
